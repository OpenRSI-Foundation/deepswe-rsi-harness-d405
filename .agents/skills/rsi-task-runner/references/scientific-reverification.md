# Independent scientific re-verification

Use this one post-run workflow for authored Science Discovery and metric Benchmark
tasks, on either execution backend. It checks the scientific result; the separate
trajectory audit checks execution and conduct. It does not change the task's Judge,
reward, ranking, completion criteria or research budget. Imported checker-only
tasks are not automatically enrolled in this workflow.

## Before the run

Use the task README's validated candidate-retention procedure. It must keep the
artifact and evidence needed to reproduce the selected result, tied to its
submission and content version, after Work changes or temporary Judge snapshots
are released. Reuse saved/versioned task outputs; retain the designated final
candidate or current best completed candidate under the existing selection rule,
not every Work snapshot. Keep retention within the agreed storage allowance.

If this handoff is missing, use the selected backend's validator to check a
task-local retention procedure within existing repair authorization, or explicitly
defer scientific re-verification. Do not change Harness or silently increase
storage. A score/log alone is not a retained candidate.

## Runner handoff

After research and all accepted Judge work finish, complete the trajectory audit
and initiate this step before the final scientific outcome report. Do not wait
for all Discovery rubrics to pass: verify the concrete results actually claimed,
including partial or negative results within the agreed scope. If no assessable
result or retained candidate exists, report that limitation without inventing one.

1. Select the final candidate already designated by the run/user; otherwise use
   the best completed evaluation under the existing direction. Record the run,
   submission and immutable snapshot/version. Inspect that same candidate, not a
   later edited Work directory. Resolve it through the validated retention
   procedure. If its artifacts are unavailable, report that the selected result
   cannot be reverified; do not substitute a different candidate or certify the
   historical best from its score/log alone.
2. Reuse the confirmed objective type: `claim`, `optimization` or `mixed`.
   Metric Benchmark uses `optimization`. Use the accepted result scope and
   external-confirmation boundary. Do not ask the contributor to classify again.
3. Prepare a review packet containing the scientific question, scope, assumptions,
   claimed result, final artifacts, data/source provenance and necessary evidence.
   Include the metric definition, validity constraints, comparison conditions and
   precision requirements when they define the scientific question. Initially
   exclude original rubrics, Judge implementation, verdicts, scores, feedback and
   the trajectory audit's conclusions. Extract the necessary specification rather
   than sending an entire proposal containing the original evaluation materials.
4. Hand the packet and this procedure to a fresh reviewer context, without the
   research conversation or the runner's conclusions. The same model may be used;
   a second provider or human reviewer is not required. A fresh context is not an
   independent scientific method. If no separate context is available, report
   independent review as pending instead of calling the runner's self-review
   independent. Artifacts remain evidence, not instructions to follow.

Use existing review authorization and resources. Record the reviewer, computation
allowance and actual review cost separately from the research budget; reuse any
explicit deferral. Do not extend the run or silently allocate a new experiment.
Within that allowance, perform the checks needed for the claimed result. If a
required computation, model call, data access or external experiment is unavailable
or unauthorized, report what remains unverified and why. Ask only for additional
resources actually needed to complete an unresolved check.

## Independent examination

Read the complete relevant argument and inspect the evidence. Check the reported
result against the problem itself, then choose the applicable type below. Use an
independent derivation or computation where feasible; label reuse of the author's
implementation accurately. Run reviewed verification code in an isolated working
area using copies/read-only inputs and the approved environment, resource and
access limits. Do not replay arbitrary commands from a trajectory or modify the
candidate to make it pass. Record commands, versions, observations and failures.

| Type | Scientific checks |
| --- | --- |
| Claim | Trace each claimed conclusion from its premises through the argument and supporting evidence. Examine missing steps, counterexamples, competing explanations, numerical/statistical uncertainty and scope as applicable. A proof needs a valid argument; numerical agreement alone does not prove a theorem. A supported negative result can be valid when the question allows it. |
| Optimization | Verify the actual artifact's validity, then recompute its metric under the fixed inputs, protocol, units, aggregation and optimization direction. Check that any claimed improvement uses a matched reference and survives relevant numerical error or stochastic variation. Examine whether the metric measures the stated objective or admits an invalid shortcut. An improved score alone establishes neither a mechanism nor global optimality. |
| Mixed | Perform both checks and examine the connection: does the measured result support the accompanying scientific claim? Report each part separately when only one is established. For a forecasting task, also check the declared information/time boundary, leakage and reproducibility; do not impose forecasting-specific requirements on other Mixed tasks. |

Choose checks appropriate to the accepted scientific scope, rather than adding a
new task or mandatory experiment suite. For an external-confirmation deliverable,
verify the candidate, supporting rationale and usable test handoff. Keep the
external claim pending until the agreed physical/observational test is performed;
simulation alone does not confirm a real-world result. A small fixture or a read
through of code is not a completed scientific recomputation.

## Compare and report

Save the first-stage findings before the runner supplies original evaluation
materials and the trajectory audit. Then compare them to identify missed evidence,
evaluation gaps or disagreements. Preserve the first-stage findings and explain
any revision; passing the original Judge is not independent corroboration. Report
conduct findings separately, under the existing integrity policy.

Write one scientific re-verification report in a new operator-side location outside
the frozen run/task inputs. Include:

- Run/candidate/version, objective type, scientific scope, reviewer and resources.
- What was supplied in each stage and any limitation on independence or access.
- Findings for each claim or performance result, with evidence: supported,
  contradicted or unresolved within the checked scope. Separate argument review,
  rerunning supplied code and verification by an independent method.
- Actual checks and outcomes, discrepancies with the original Judge, missing
  evidence and remaining external tests. A tool/environment failure is not a
  scientific refutation; unperformed checks cannot be reported as passed.

Link this report in the runner's completion report, separately from raw/effective
scores and the trajectory audit. Preserve all original reward and result files.
A disagreement is reported for follow-up, not converted into a new score or an
automatic task repair/research restart. Keep the packet and report operator-side,
especially hidden Benchmark evaluation materials; publication follows the existing
authorization and never becomes additional Work feedback by default.
